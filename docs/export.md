# Exporting from a live cluster

Normally you keep your Argo CD manifests in Git, so you can check them out and point OctoDoctor at the
directory that holds them.

Sometimes you only have the cluster. Instead of first exporting the manifests yourself with
`argocd admin export` or `kubexporter` and then running OctoDoctor on the result, use `--export` to do
both in one step:

```bash
./octodoctor --export
./octodoctor -e
```

OctoDoctor connects to your cluster with the standard kubeconfig, saves the Argo CD manifests it cares
about into a local directory, and then analyses that directory exactly as if you had passed it with
`--directory`. The report ends up inside the exported directory.

## Choosing the context and the namespace

Without any further arguments, OctoDoctor uses the current context of your kubeconfig and reads the
`argocd` namespace, which matches a default Argo CD installation.

```bash
# The current kubeconfig context, namespace argocd
./octodoctor --export

# A specific context
./octodoctor --export --context production
./octodoctor --export -c production

# A specific namespace
./octodoctor --export --namespace my-argocd
./octodoctor --export -n my-argocd
```

If your kubeconfig has no current context, OctoDoctor stops and asks you to choose one with `--context`.

!!! note "`--export` and `--directory` are mutually exclusive"
    `--export` analyses a cluster and `--directory` analyses a local folder, so passing both is an
    error. If you pass neither, the current directory is analysed.

## Where the files go

The manifests are written to `argocd-manifests-export-<context>` in your current directory, with one
subfolder per resource type and one file per resource:

```
argocd-manifests-export-production/
├── applications/
│   ├── team-a-billing.yaml
│   └── team-b-billing.yaml
├── applicationsets/
│   └── billing-application-set.yaml
├── appprojects/
│   └── default.yaml
├── configmaps/
│   ├── argocd-cm.yaml
│   └── argocd-rbac-cm.yaml
├── secrets/
│   └── argocd-secret.yaml
└── octodoctor-output/
    ├── index.html
    ├── report.json
    └── report.yaml
```

Characters that are not safe in a directory name are replaced with a dash, so an EKS context called
`arn:aws:eks:eu-west-1:123456789:cluster/prod` becomes
`argocd-manifests-export-arn-aws-eks-eu-west-1-123456789-cluster-prod`.

The exported files are **not** deleted when the analysis finishes. They stay on disk so you can read
them, commit them, or analyse them again later with `--directory`. If the directory already exists from
an earlier export, OctoDoctor deletes it and creates it again, so that manifests of resources that no
longer exist in the cluster are never analysed. A log line tells you when this happens.

## What gets exported

Only the resources OctoDoctor already knows how to analyse:

| Resource type | What is exported |
|---|---|
| `Application` | all of them, including the ones generated by an ApplicationSet |
| `ApplicationSet` | all of them |
| `AppProject` | all of them |
| `ConfigMap` | only the Argo CD settings: `argocd-cm`, `argocd-cmd-params-cm`, `argocd-rbac-cm`, `argocd-tls-certs-cm` and `argocd-ssh-known-hosts-cm` |
| `Secret` | only `argocd-secret` and the external cluster secrets labelled `argocd.argoproj.io/secret-type: cluster` |

Every other ConfigMap and Secret in the namespace is ignored.

The files are saved in the simplest form possible. Everything that only describes the live object in the
cluster is removed, so what is left looks like a manifest somebody would commit to Git: `status`, the
`metadata` fields `uid`, `resourceVersion`, `generation`, `creationTimestamp`, `selfLink`,
`managedFields`, `deletionTimestamp`, `deletionGracePeriodSeconds`, `ownerReferences` and `finalizers`,
and the `kubectl.kubernetes.io/last-applied-configuration` annotation.

!!! warning "Secret values are redacted"
    OctoDoctor keeps the **keys** of a Secret but replaces every **value** with
    `REDACTED-BY-OCTODOCTOR`, so no password, token or private key is ever written to your disk. The
    rules only ever look at the key names of a Secret, so this does not change any result.

Even with the Secret values redacted, the exported manifests still describe how your Argo CD is
configured, for example your RBAC policy and your single sign-on settings. The exported directory is
therefore readable only by you, and so is the report inside it. Copy the report somewhere else if you
want to share it.

## Permissions

OctoDoctor only reads, and never writes to your cluster. It needs `list` permission on Applications,
ApplicationSets, AppProjects, ConfigMaps and Secrets in the namespace you point it at.

If you are not allowed to list one of these, or the Argo CD CRDs are not installed on the cluster at
all, OctoDoctor logs a warning, skips that resource type and carries on with the rest. Only a cluster it
cannot reach, or credentials it cannot authenticate with, stop the run.
