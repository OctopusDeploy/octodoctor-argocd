# R25 – More than two sources

!!! warning "Severity: Medium"

Applications with more than 2 sources need a different grouping mechanism.

## Why this matters

Argo CD's multi-source feature was designed for one specific problem: you want to deploy a Helm
chart you don't own, from a Helm repository or OCI registry, configured with value files you do own,
from your own Git repository. That's two sources, and there's no other clean way to express it.

It isn't a general grouping mechanism. Once an Application lists three, four, or six sources, it has
stopped modelling one deployable thing and started being a folder. That costs you the things an
Application is for. Sync status, health, and history are reported for the Application as a whole, so
one unhealthy component makes the whole group look broken and you can't tell which. Sync waves and
rollbacks apply to everything at once. You can't give one component a different sync policy, a
different project, or a different destination namespace. And the Argo CD UI shows one node where you
wanted six.

The grouping you actually wanted is usually an ApplicationSet, which generates one Application per
component from a single manifest, or an app-of-apps Application whose job is to create the others.

## How to fix it

Keep multi-source Applications to two sources: the chart and its values. Split anything else into
separate Applications, generated by an ApplicationSet.

**Flagged by this rule**

```yaml
spec:
  sources:
    - repoURL: https://github.com/mycompany/billing-app.git
      path: manifests
      targetRevision: HEAD
    - repoURL: https://github.com/mycompany/common-settings.git
      path: configmaps-billing
      targetRevision: HEAD
    - repoURL: https://github.com/mycompany/prod-settings.git
      path: prod-values
      targetRevision: HEAD
```

**Passes**

```yaml
spec:
  sources:
    - repoURL: https://github.com/mycompany/billing-app.git
      path: manifests
      targetRevision: HEAD
    - repoURL: https://github.com/mycompany/common-settings.git
      path: configmaps-billing
      targetRevision: HEAD
```

Applications using the single `spec.source` field are inactive for this rule, as are Applications
with no sources at all.

## Exceptions

A third source is occasionally hard to avoid, for instance a chart, a shared values repository, and
a per-cluster values repository that genuinely can't be merged. Before accepting it, check whether a
Helm value hierarchy inside one repository expresses the same layering — that's usually what the
extra source is standing in for.
